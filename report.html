Design rationale

4 / 7

Why this split

Ownership

  • MySQL owns what the limit is and what is registered (keys, paths, upstreams). Survives restarts; config changes without redeploying the proxy.
  • Redis + Lua owns how much has been consumed. All proxy replicas share the same counters under contention.

Plane separation

  • Control plane mutates config only — no forwarding, no load generation.
  • Data plane enforces on the request path — evaluate, then forward or deny.
  • Auth is explicitly out of scope on both planes.

Control plane

5 / 7

Configure

Admin surface for rate-limiter configuration. Durable config is written here and read by the data plane at evaluation time.

ComponentResponsibility
React — Control Plane tab Operator console for CRUD on keys, paths, upstreams, and rate-limit rules; view registration state
Control Plane API (Go) REST admin APIs backing the UI; validates and persists config
MySQL Source of truth for keys, path mappings, upstream targets, and policies (burst / sustained, algorithm)
  • Key — tenant / client identifier (rate-limit subject)
  • Path — request path / namespace the limit applies to
  • Upstream — backend target for allowed traffic

Data plane

6 / 7

Enforce + validate

Inline reverse proxy: rate-limit decision first, then forward. No authentication. Vegeta validates under load.

ComponentResponsibility
React — Data Plane tab Configure and trigger Vegeta profiles; observe allow/deny / quota signals
Vegeta load client (Go) Configurable ramp, burst, and constant load against the proxy
Inline reverse proxy (Go) ×2 Evaluate via Redis/Lua; allow → forward upstream; deny → reject with quota signals; shared state across replicas
Mock backend (Go) Dummy APIs with random delay; proves forward-on-allow without business logic
Redis + Lua / MySQL / Compose Atomic counters; policy + routing reads; local bootstrap of the stack

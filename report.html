Store choice — why Mongo vs Redis

MongoDB — policy of record

Holds what to limit: namespaces, match rules, and algorithm configs. Control plane is the sole writer; data plane polls (~2s) and caches for hot-reload without restart.

Redis + Lua — hot path counts

Chosen for quick, in-memory, atomic check-and-consume under contention. One EVAL per request keeps multi-proxy quotas correct — no double-count across replicas.

Backfill & reset: fixed_token refills on each Lua call (elapsed × sustainedRps, capped at burst) — idle keys start full. fixed_window resets when windowId rolls (new key + PEXPIRE). sliding_window trims expired ZSET members each consume; reset_ms is when the oldest request leaves the window. Keys self-expire via TTL — no manual backfill job.

Functional supportability

  • Namespace create — requires valid configId, upstreamHost, algorithm, matchMode; enabled + priority control pickup.
  • Rule create — attach matchers (header / path / path_attr / method / regex); namespace matchMode AND/OR combines them.
  • Config swap — PUT namespace configId to change limits without rewriting rules.
  • Safe delete — config delete blocked if namespaces reference it; namespace delete cascades its rules.
  • Disable without delete — set enabled: false on namespace / rule / config to pause enforcement.

* Rate-limiter service needs no reload / restart when policy is added or changed — proxies poll Mongo (~2s), refresh the in-memory cache, and enforce the new namespaces / rules / configs on the next request.
